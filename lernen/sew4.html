1.1 Aufbau einer JavaFX-App

public class HelloApplication extends Application {
    @Override
    public void start(Stage stage) {           // abstrakte Methode von Application
        Scene scene = new Scene(new Label("Welcome"), 250, 100);
        stage.setTitle("Hello");
        stage.setScene(scene);

2.2 Datentypen

  • Werttypen (int, bool, double, char, decimal, enum, struct): Daten direkt (Stack), Zuweisung kopiert den Wert
  • Referenztypen (class, interface, string, Arrays, object): Referenz am Stack, Objekt am Heap, Zuweisung kopiert die Referenz → mehrere Variablen zeigen auf dasselbe Objekt
  • string ist ein Referenztyp, aber immutable. char = 1 Unicode-Zeichen, 2 Byte
  • decimal für Geld: Literal mit m (9.50m), float mit f, long mit L

2.5 Variablen, var, Safe Calls

  • Variable = lokale Variable, Parameter (value/ref/out/in), Feld (instance/static), Array-Element
  • Lokale Variablen müssen vor Verwendung zugewiesen sein (sonst Compilerfehler CS0165). Felder und Array-Elemente bekommen automatisch Default-Werte (0, false, null)
  • var x = "Hello"; → Typ wird vom Compiler aus der Zuweisung bestimmt (statisch typisiert, nur bei lokalen Variablen, nur mit Initialisierung)

3 OOP – Classes

3.1 Klasse & Modifier

class = häufigster Referenztyp. Klassen-Modifier: public, internal (Default, nur im Projekt), abstract, sealed, static, unsafe, partial. Member: Felder, Methoden, Properties, Indexer, Events, Konstruktoren, Finalizer, Operatoren, verschachtelte Typen.

3.2 Felder: readonly vs. const

class Octopus
{
    public readonly string Name;        // zur LAUFZEIT; nur bei Deklaration oder im Konstruktor setzbar
    public readonly int Legs = 8;       // jedes Objekt hat eigene readonly-Felder
    public const int MaxArms = 8;       // zur COMPILE-Zeit; implizit static; Wert MUSS bei Deklaration stehen
    public Octopus(string name) { Name = name; }
}
new Octopus("Jack").Name = "Alice";     // Compilerfehler CS0191
const readonly
Wert bekannt Compile-Zeit Laufzeit
setzbar nur bei Deklaration Deklaration oder Konstruktor
pro Objekt? nein (implizit static), Zugriff Klasse.Name ja
Typen eingebaute Typen (int, double, decimal, string, enum …) beliebig

3.3 Methoden

  • Signatur = Name + Anzahl Typparameter + Typ und Übergabeart (ref/out/in/value) der Parameter. Nicht Teil der Signatur: Rückgabetyp, Parameternamen, params, Zugriffsmodifier. → Zwei Methoden, die sich nur im Rückgabetyp unterscheiden = Compilerfehler.
  • Overloading = gleicher Name, unterschiedliche Parametertypen/-anzahl
int Twice(int x) => x * 2;                          // expression-bodied
void Show(int x) => Console.WriteLine(x);

void WriteCubes()
{
    int value = 3;
    Console.WriteLine(Cube());
    int Cube() => value * value * value;            // lokale Methode: sieht lokale Variablen
}
void WriteCubes2()
{
    Console.WriteLine(Cube(3));
    static int Cube(int v) => v * v * v;            // STATIC lokale Methode: sieht KEINE lokalen Variablen/Parameter
}

3.4 Konstruktoren

public class Wine
{
    public decimal Price; public int Year;
    public Wine(decimal price) { Price = price; }
    public Wine(decimal price, int year) : this(price) { Year = year; }        // Chaining mit this(...)
    public Wine(decimal price, DateTime d) : this(price, d.Year) { }          // Ausdruck als Argument
}
public class Panda(string name, int age)                                     // Primary Constructor (C# 12)
{
    public string Name { get; set; } = name;
    public int Age { get; set; } = age;
}
public class Panda2 { private string _name; public Panda2(string n) => _name = n; }   // expression-bodied
  • Default-Konstruktor (parameterlos) wird nur generiert, wenn die Klasse gar keinen Konstruktor hat. Ein selbst geschriebener parameterloser ist kein Default-Konstruktor.
  • Sobald man Panda(string n) schreibt, geht new Panda() nicht mehr.
  • private Konstruktor → kein new von außen (Singleton, Helper-Klasse nur mit static Methoden)
  • static Konstruktor static Test() { }: kein Modifier, keine Parameter, max. 1, läuft genau einmal automatisch vor dem 1. Objekt / 1. static-Zugriff, vor dem Instanz-Konstruktor

3.6 Properties – alle Varianten

private decimal _price;                                  // Backing Field
public decimal Price
{
    get { return _price; }
    set { _price = value < 0 ? 0 : value; }             // value = impliziter Parameter
}
public decimal Price2 { get => _price; set => _price = value; }     // expression-bodied Accessoren
public decimal Worth => _price * _shares;                            // read-only, berechnet (nur get)
public decimal Current { get; set; }                                 // Auto-Property (Compiler erzeugt Feld)
public decimal Start { get; set; } = 123;                            // Property-Initializer
public int Maximum { get; } = 999;                                   // get-only: nur Initializer/Konstruktor
public decimal X { get; private set; }                               // unterschiedliche Sichtbarkeit
public int Pitch { get; init; } = 20;                                // init-only: nur Konstruktor/Object Initializer
var note = new Note { Pitch = 50 };   // OK
note.Pitch = 200;                     // Fehler CS8852 (init-only)

3.7 Static Class, Finalizer, Partial

  • static class: kein new, kann nicht vererbt werden, nur static Member (z. B. Console, Math). Alternative: normale Klasse + private Konstruktor
  • Finalizer ~DemoA() { }: läuft auf eigenem Finalizer-Thread, bevor der GC das Objekt entfernt. Besser: IDisposable/Dispose() (deterministisch)
  • partial: Klasse/Methode über mehrere Dateien aufteilen (jeder Teil mit partial). Partial-Methode ohne Zugriffsmodifier: muss void sein, kein out, implizit private, Implementierung optional. Mit Modifier: muss implementiert werden, keine Einschränkungen.

4 OOP – Inheritance

4.1 Grundlagen & Polymorphie

public class Asset { public string Name { get; set; } }
public class Stock : Asset { public long SharesOwned { get; set; } }     // nur EINE Basisklasse
public class House : Asset { public decimal Mortgage { get; set; } }

static void Display(Asset a) => Console.WriteLine(a.Name);
Display(new Stock { Name = "MSFT" });     // Polymorphie: Asset-Variable kann Stock/House referenzieren

4.2 Casting

Syntax erfolgreich?
Upcast (Sub → Super) Asset a = stock; (implizit) immer
Downcast (Super → Sub) Stock s = (Stock)a; (explizit) nur wenn Objekt passt, sonst InvalidCastException
as Stock? s = a as Stock; liefert null statt Exception
is if (a is Stock) / if (a is Stock s) …s.SharesOwned prüft; Pattern-Variable spart den Cast
  • Casts ändern nur die Referenz, nicht das Objekt: stock == asset → True
  • Über eine Asset-Referenz sieht man nur Asset-Member: asset.SharesOwned → Compilerfehler CS1061

4.3 virtual / override / abstract / new / sealed

public class Asset
{
    public virtual decimal Liability => 0;              // darf überschrieben werden
}
public class House : Asset
{
    public decimal Mortgage { get; set; }
    public override decimal Liability => Mortgage;      // überschreibt
}
Asset a = new House { Mortgage = 300000 };
Console.WriteLine(a.Liability);                          // 300000  ← Objekttyp entscheidet (dynamisch)

public abstract class AbstractAsset { public abstract decimal NetValue { get; } }  // ohne Rumpf
public class Plot : Asset { public sealed override decimal Liability => 1; }     // darf nicht weiter überschrieben werden
public class B : A { public new int Counter = 2; }                                // HIDING (verdecken)
Schlüsselwort Bedeutung
virtual Basisklasse erlaubt Überschreiben
override Unterklasse überschreibt; Signatur, Rückgabetyp und Sichtbarkeit identisch
abstract kein Rumpf, Unterklasse muss überschreiben; Klasse muss dann auch abstract sein. Abstrakte Klasse: kein new, darf aber 0 abstrakte Member haben
new verdeckt einen geerbten Member (kein Polymorphismus!), unterdrückt Warnung CS0108
sealed Member: nicht weiter überschreibbar · Klasse: nicht vererbbar
base base.Liability (Basis-Version aufrufen) · : base(x) (Basis-Konstruktor)

override vs. new: Bei override entscheidet der Objekttyp (Laufzeit). Bei new entscheidet der Variablentyp (Compile-Zeit). Überschreibbar sind Methoden, Properties, Indexer, Events.

4.4 Konstruktoren & Vererbung

  • Konstruktoren werden nicht vererbt → jede Unterklasse definiert ihre eigenen, ruft mit : base(...) die Basis auf
  • Nach : steht genau ein Aufruf: base(...) oder this(...)
  • Ohne : base(...) wird der parameterlose Basis-Konstruktor aufgerufen. Gibt es den nicht → Compilerfehler

Initialisierungs-Reihenfolge in C# (new Cc(5) mit Cc : Bb : Aa):

  1. Feld-Initialisierer von unten nach oben (Cc → Bb → Aa), dabei werden jeweils die base(...)-Argumente ausgewertet
  2. Konstruktor-Rümpfe von oben nach unten (Aa → Bb → Cc)
Ausgabe:  Aa 7   Bb 6   Cc 5

In Java laufen Feld-Initialisierer nach dem Superkonstruktor, also direkt vor dem eigenen Konstruktor-Rumpf. Unterschied merken!

5.3 Interfaces

public interface IShape
{
    const int MaxSides = 12;                    // ab C# 8: Konstanten
    static int Count;                           // ab C# 8: static Felder
    double Area { get; }                        // abstrakt (implizit public)
    string Describe() => $"Area: {Area}";       // ab C# 8: Default-Implementierung
}
public interface IRedoable : IUndoable { void Redo(); }    // Interface erweitert Interface
  • Member sind implizit public abstract. Nicht erlaubt: Instanzfelder, Instanzkonstruktoren, Finalizer
  • Klasse: eine Basisklasse, aber mehrere Interfaces. Struct: keine Basisklasse, mehrere Interfaces
  • Implementierte Interface-Methoden ohne override! Sie sind standardmäßig sealed → zum Überschreiben in der Basisklasse virtual (oder abstract) machen
  • Default-Member sind nur über das Interface aufrufbar: ((ILogger)logger).Log("x"), nicht über logger.Log("x")

Explizite Implementierung (bei Namenskollision oder zum Verstecken):

interface I1 { void Help(); }   interface I2 { int Help(); }
public class Widget : I1, I2
{
    public void Help() => Console.WriteLine("I1.Help");     // implizit
    int I2.Help() { Console.WriteLine("I2.Help"); return 42; }   // explizit: KEIN public!
}
w.Help();          // I1.Help
((I2)w).Help();    // I2.Help   ← nur über Interface-Referenz erreichbar

6 Nullability

  • Werttypen können normal nicht null sein → int? (= Nullable<int>), Wert mit .HasValue / .Value oder ?? 0
  • Nullable Reference Types (<Nullable>enable</Nullable> im .csproj, Standard bei neuen Projekten): string s = soll nie null sein, string? s = darf null sein. Der Compiler gibt Warnungen (keine Fehler!), z. B. CS8600 „Converting null literal …“, CS8602 „Dereference of a possibly null reference“, CS8618 „Non-nullable property must contain a non-null value when exiting constructor“
string? name = Console.ReadLine();             // ReadLine liefert string?
int len1 = name.Length;                        // Warnung CS8602
int len2 = name?.Length ?? 0;                  // sicher
if (name != null) Console.WriteLine(name.Length);   // nach null-Check weiß der Compiler: nicht null
Person? p = FindPerson("x");
string city = p?.Address?.City ?? "unbekannt";       // Ketten: bricht beim ersten null ab
public string Name { get; set; } = "";               // gegen CS8618: Default-Wert setzen
Flower f = null!;                                    // ! = "Ich weiß, was ich tue" (nur Warnung weg)
Operator Name (dt.) Wirkung
a ?? b Null-Verbindungsoperator a, außer a ist null → b
a ??= b Null-Verbindungszuweisung if (a == null) a = b;
a?.B Null-Bedingungsoperator (Elvis) a == null ? null : a.B
a! Null-forgiving unterdrückt nur die Warnung, zur Laufzeit trotzdem NullReferenceException möglich

p?.Name.Length → ist p null, wird die ganze Kette übersprungen. Ergebnis eines ?. bei int ist int?.

7 UML: Klassen- und Objektdiagramm

7.1 Klassendiagramm

  • Strukturdiagramm, statischer Blick: Name, Attribute, Methoden, Beziehungen. Teil von UML (Unified Modeling Language)
  • 3 Abschnitte: Name (ggf. «interface», «enumeration», kursiv = abstract) · Attribute · Methoden
  • Sichtbarkeit: + public, - private, # protected, ~ package; static = unterstrichen
  • Schreibweise: - weeks: WeeklyMealPlan[52], + AddMenu(week: int, menu: Menu): void

7.2 Beziehungen

Beziehung Symbol Bedeutung Code
Generalisierung / Vererbung Linie mit leerem Dreieck zur Basisklasse „is a“ class WatchDog : Dog
Realisierung gestrichelt + leeres Dreieck zum Interface „behaves like“ class Poodle : IDog
Assoziation Linie (mit Pfeil = gerichtet/navigierbar) „has a“ Referenz-Attribut
Aggregation leere Raute beim Ganzen „part of“, Teile leben unabhängig Referenz, von außen übergeben
Komposition gefüllte Raute beim Ganzen stärkste Form, Teile existenzabhängig, vom Ganzen erzeugt/zerstört private readonly Roof roof = new Roof();
Abhängigkeit gestrichelter Pfeil nur kurz benutzt: lokale Variable, Parameter, static-Aufruf B.Foo() in einer Methode

Stärke: Assoziation < Aggregation < Komposition. Im Code gibt es keinen syntaktischen Unterschied zwischen Aggregation und Komposition: der Unterschied liegt in Verantwortung und Lebenszyklus.

Multiplizitäten: 0 · 0..1 · 1 (= 1..1) · 0..* = * · 1..* Navigierbarkeit: Pfeil zeigt zur Klasse, auf die eine Referenz gehalten wird (navigierende Klasse → Zielklasse). Ohne Pfeile = bidirektional/unspezifiziert, ✕ = nicht navigierbar.

public class House
{
    private readonly Roof _roof = new Roof();            // Komposition 1
    private Room[] _rooms = { new Room(), new Room() };  // Komposition 1..*
    private Garage? _garage;                             // Aggregation 0..1
    private Person[] _persons;                           // Aggregation 0..*
}

7.3 Objektdiagramm

  • Momentaufnahme des Speichers zu einem bestimmten Zeitpunkt: konkrete Objekte und Links
  • Notation: name : Klasse bzw. :Klasse (anonym), unterstrichen; darunter Attributwerte name = "Rex"
  • Keine Methoden, keine Multiplizitäten, nur echte Verbindungen zwischen Objekten

8 Typische Test-Fallen (Checkliste)

  1. Feld-Initialisierer-Reihenfolge: C# von unten nach oben, Konstruktor-Rümpfe von oben nach unten.
